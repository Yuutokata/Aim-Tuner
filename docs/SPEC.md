# Specification

## Goal

An open-source Windows desktop app that lets any player find their optimal mouse sensitivity and, optionally, an optimal acceleration curve in a built-in 3D aim trainer. Results are shown as a game sensitivity (Valorant first) and cm/360°, and optionally exported as a Raw Accel `settings.json`. The app is not tailored to a specific user; all user values come from onboarding or settings.

## Hard rules (anti-cheat safety)

1. No interaction with game processes: no injection, no game memory access, no input manipulation outside the app window, no automatic game config edits.
2. Mouse input is read only while the app window is focused.
3. Accel curves are simulated in-app and exported as a file for Raw Accel. No custom driver.

## Tech stack

Kotlin, JDK 21, Gradle Kotlin DSL; LibGDX (LWJGL3) with Scene2D; Raw Input via JNA with QPC timestamps (fallback GLFW raw motion) behind `RawMouseSource`; SQLite (xerial JDBC) in `%APPDATA%/AimTune`, settings as JSON (kotlinx.serialization); custom Gaussian process (own Cholesky, no linear algebra library, see ADR 0004); I18NBundle (en default, de); native open/save dialogs through LWJGL tinyfd (same version as LibGDX's LWJGL); jpackage; GitHub Actions; MIT.

## Features

### Units and game converters
- Internal unit cm/360°: `cm360 = (360 × 2.54) / (DPI × sens × yaw)`.
- Games are `GameProfile`s (interface and/or JSON in `games/`): name, yaw (deg/count at sens 1), FOV with type (horizontal/vertical), aspect ratio behavior, sensitivity format and rounding.
- Valorant: yaw 0.07, FOV 103° horizontal (16:9), to be verified against current sources.
- New games without core changes. The trainer renders with the selected profile's FOV.

### Onboarding (editable later)
- DPI, game, current sensitivity → current cm/360° as start point.
- Aim style: wrist / mixed / arm. Mousepad: small / medium / large or width in cm.
- Derive a search range in cm/360° from a configurable table; pad width caps the upper bound; the current value is always inside the range.
- Notice (not enforced) that Windows "Enhance pointer precision" and active Raw Accel curves distort measurements.

### Scenarios
Rounds of about 30-60 s (configurable) in a minimal map (floor at eye height, a far wall, corners and doorways) with targets of a head's angular size, defined per game in its profile: Flick, Micro-adjust, Tracking, Target switching, Flash turn-away. Plugin-style `Scenario` interface; seeded for reproducibility.

**Range mode.** A scenario that rebuilds the function of a shooting range for games whose profile has a `trainer.range` block (Valorant): one humanoid bot at a time stands on the floor in front of a counter, strafes (or stands, a setting) and is killed by a head hit or several body hits; the next one appears a moment later. It is called "Range mode" and its look is original (docs/RANGE.md, docs/DESIGN.md). A round counts kills, the time to kill and the first-shot head hits, and scores accuracy and time to hit with its own baseline. Optional settings: a speed preset (bots leave after 3.0 / 2.0 / 1.2 s, or never) and Bots Strafe / Stand still. It is part of the default scenario set of a game with a Range block (flick, range and flash; saved settings keep their scenarios, and the settings tile still switches it), and the main menu entry "Range mode" (M) starts a blind sensitivity test of range and flick rounds in equal shares, whatever the toggles say, with its speed and bots settings; its rounds count like other blind rounds. The curve finder does not play range rounds. The values of the profile block are measurements from the user's own recordings or assumptions, all marked `verified: false`.

**Crosshair.** Players aim differently with an unfamiliar crosshair, so the trainer draws the player's own Valorant crosshair in all scenarios: pasted as a profile code or built in the editor (colors, outlines, center dot, inner and outer lines with the ranges of the game), with named profiles, a live preview and export of the code back into Valorant. Sizes are screen pixels at the native resolution; movement and firing error are kept in the code but not drawn (docs/CROSSHAIR.md).

**Heights.** Valorant fights are on one level, so most targets stand at head height, within a few degrees of the crosshair, and only a small share is above or below (heaven positions, ramps, stairs, crouching players). The profile holds the camera's eye height, the head height and this vertical distribution (`trainer.elevation`); a fully 3D field is available only for comparisons. A share of the flick and switching targets stands at a corner or doorway of the map (`trainer.arena`), so players can place the crosshair at head height there. The results screen says which axis the misses of the first movements come from ("most of your misses are vertical").

**Flash turn-away.** Turning away from a flash and coming back quickly is a key use case in Valorant. A flash orb becomes visible inside the field of view and pops after a short delay; the player has to turn so far that the flash is beyond the edge of the screen (half the profile's horizontal FOV plus a margin) when it pops, then turn back and hit the head-sized enemy that appears near the original view direction. A player who still sees the flash is blinded (white screen) for its blind duration and sees the enemy only afterwards. Times, positions and the blind duration are in the `flash` block of the profile's `trainer` block (windups of the real abilities, 0.3-0.6 s; sources and what is assumed are listed in the profile and in docs/ALGORITHMS.md). A setting in onboarding (aim style step) and in the settings says how much flash dodging matters to the player (never / sometimes / often); it is the weight of the dodge metric and decides how often flash rounds are played. Cue sounds (alert, rising whine, pop, ringing when blinded; synthesized, switchable) tell when to turn away and when it is safe to turn back.

**Hit sound.** Every hit on a target plays a short, crisp sound (synthesized from scratch, switchable in the settings). Its pitch climbs a pentatonic scale with each hit in a row and starts again after a miss, which rewards clean streaks. Tracking has no clicks and therefore no hit sound.

**Update hint.** At most once a day the app asks the GitHub API for the newest release of its repository (`app/update`, plain HTTPS GET, no account, no identifier beyond `User-Agent: AimTune/<version>`). If the release is newer than the running build, the main menu shows "Version x is available (U)"; the key or a click opens the release page in the browser. Nothing is downloaded or installed. Every failure (offline, rate limit, a private repository, which GitHub answers with 404, odd data) shows nothing at all. The check can be switched off in the settings (`checkForUpdates`) or with `--no-update-check`.

### Measurement and metrics
Store raw events (counts + timestamps) and target events per round. Compute hit rate, time-to-target, signed endpoint error per movement, corrective movements, path efficiency, tracking time-on-target ratio and mean distance. Segment into submovements (also used for accel analysis). For flash rounds also the share of flashes the player had turned away from when they popped, the time to turn away and its peak speed. Combine accuracy (first shot), time to hit, tracking and the flash dodge rate into a normalized, weighted, per-user-baselined score; the spread of the first-movement error is shown as a diagnostic only because it cannot have an optimum of its own.

### Sensitivity optimization (phase 1)
Bayesian optimization over log(cm360) in the range; GP with noise model; EI or UCB; blind testing; repeated points for noise; session offsets and a per-session trend (learning, fatigue) are part of the model, a detected trend lowers the confidence; stop at any time with confidence value and recommendation whether more rounds are worthwhile; sessions merge into one result.

### Acceleration curve (phase 2, optional)
A new blind search builds on the stored searches at the same setup (fewer new rounds); the intro has a switch to start it from nothing instead, which tries the whole strength range again and deletes nothing. The blind search of the curve strength and its blind test also play flash turn-away rounds (half of their rounds) when flash dodging matters to the player; the error analysis of phase 1 plain rounds does not use them (docs/ALGORITHMS.md "Flash turn-away").

Base sensitivity of the curve runs is the player's configured game sensitivity (as cm/360°); the sensitivity finder's optimum replaces it only if its confidence is at least 50 % and the player switches that on in the intro. Signed endpoint error vs input speed from submovements gives a desired gain g(v). Fit the supported Raw Accel modes (verify list) with a weighted least squares fit on the median error per speed bin, pick the mode by an information criterion (BIC) against "no acceleration", constrain with caps. The calibration also uses the plain rounds of earlier runs at about the same sensitivity (3 %), so the data can grow over several days; the blind search and the A/B test stay per run. Verify via in-app blind A/B; the result screen of the test offers the export only if the curve was measurably better, else recommend no accel. The "Last analysis" and "Last search" screens do not export: they offer only the blind test of the curve they found (the search only when its result is clear, see docs/ALGORITHMS.md "Curve safety"), and the export follows a passed test. Export Raw Accel `settings.json` (verify schema in a1xd/rawaccel) with the sens multiplier set so in-game sensitivity stays unchanged. Since M14 the curve finder v2 (default; `--curve-finder legacy` restores the old one) bounds a found curve to the hand speeds the calibration measured. It is tested and exported as a Raw Accel lookup table that stays flat outside them, because the data say nothing about faster or slower hands. The blind strength search keeps its natural curves.

**Raw Accel hub (M22f).** The main menu item "Raw Accel" (A) opens a hub. At the top the "Runs use" card shows the sensitivity every Raw Accel run is played at (game, in-game sensitivity, cm/360°, DPI, and whether it comes from the settings or from the finder's optimum ticked in "Find a curve"); "Change in Settings" opens the settings and returns to the hub on Save or Back. The same line is on the finder intro, the refine import, the between-rounds and stage screens. The hub shows the last imported profile (only the file's path is remembered in the settings, never its content; it is read again when the hub opens, and nothing special is shown if the file is gone). The section "Curve" holds Find a curve, Refine my curve (with the note that it changes a curve only after a clear blind win, which rarely happened in testing), Last search and Last analysis. The section "Other settings" has one row for each remaining setting of Raw Accel 1.7.1 with a one-line state and its own page: what the setting does (words and formula), the value in the imported profile, the recommended value and why. Analysis rows (rotation, Y/X, L/R) are judged from the stored plain rounds (first movements against the target, docs/ALGORITHMS.md "Passive setting analyses") and show the value, its 95 % range and the number of reaches, or "not enough data: n of m". Info rows (U/D with only the measured number, angle snapping with the replay of the stored rounds, input speed cap with the speed percentiles, smoothing, domain and range stretch, whole or by component and Lp norm, polling rate and time) say why AimTune does not measure them and recommend off, 1/1, whole with 2, or automatic. The analyses are computed in the background from the newest 120 plain rounds and again only after new rounds were stored.

**Patched copy (M22f).** Passive recommendations are opt-in: on the page of an analysis row with a recommendation and an imported profile, "Add to my patched copy (not blind-tested)" is off by default and kept for the session. The patched copy is one copy of the player's file with the profile added as `<name> (AimTune)`: the curve changes of a won refine run (curve-shape whitelist) first, then the ticked rotation, Y/X and L/R values as a second patch step that changes only those keys of the new profile. The refine result screen and the hub's "Export patched copy" button (enabled with an imported profile and a refine result or a ticked recommendation) write the same copy; the screen lists every changed field and marks passive ones "not blind-tested". Save as, the export folder and the clipboard work as on the other result screens.

**Refine my Raw Accel curve (M18).** For players who already use a Raw Accel curve. The player opens their `settings.json` with a native file dialog ("Open settings.json...", M22d), pastes its text from the clipboard or drops it into `<data dir>/imports/`, picks a profile, and sees what was read and the curve. The trainer plays every setting of the profile exactly as the Raw Accel 1.7.1 driver would (curve, rotation, angle snapping, ratios, speed cap, stretches, by-component mode, smoothing, output DPI, report timing, integer output with carry; docs/ALGORITHMS.md "Raw Accel driver model (M22)"), so a profile is refused only when Raw Accel itself would reject it; a device DPI that differs from the DPI in the settings is refused too, and odd device settings (disabled, extra info, output smoothing, another profile mapped to the device) are shown as warnings. The trainer then plays the player's own profile at their game sensitivity (Raw Accel has to be off). After 8 warm-up rounds with the curve, up to two blind parts of 12 rounds each try small changes to the shape of the curve, one parameter at a time: high-speed gain and transition. Refine never changes the base of the profile (game sensitivity, output and device DPI, ratios, rotation, snap, speed cap, the multiplier at low speed); only curve-shape fields move, and the profile is changed in those fields only in the export too. After every part the player sees the best change with its range and confidence and can continue, skip the rest or go to the test. Only changes whose range stays clear of "no change" are carried on. A blind A/B test of the refined profile against the player's own profile (same targets in each pair) decides; only "better" offers an export: a copy of the player's file with the refined profile added as `<name> (AimTune)`, written to `<data dir>/exports/rawaccel/` or to a place the player picks with a native "Save as..." dialog, never into Raw Accel's folder, with the changed fields listed old to new (the clipboard stays as a way out). Supported: classic, natural, lookup table, jump (high gain only for a hard step) and synchronous (transition only); by-component profiles change both axes by the same factor. A profile with no supported part (no acceleration, power curve, some jump or synchronous profiles) cannot be refined: the import screen says so and offers no start.

### Results view
Recommended sensitivity for the selected game, cm/360°, confidence; score vs cm/360° chart with uncertainty band; accel curve chart, A/B comparison, export; session history.

## Quality strategy
Unit tests for converters (800 DPI, sens 0.249 → about 65.6 cm/360°), GP, acquisition, segmentation, curve fitting. A simulated player (Fitts' law + noise + known optimal sensitivity and gain curve) verifies convergence. Separation: core, input, app, games.
